# AI Telemetry Bridge: контракт 1.0.0, диагностическая политика 0.1.0

Подготовлено в рамках этапа 1. Это контракт, синтетический корпус и проверочный эталон, а не установленный Bridge. Производители в `windows/`, рабочие снимки, настройки клиентов и внешние провайдеры этим изменением не затрагиваются. Совместимость SDK и измерения прототипа описаны отдельно в [ai-telemetry-compatibility.md](ai-telemetry-compatibility.md). Статус всей работы ведётся в [плане](ai-telemetry-bridge-plan.md).

## Файлы и версии

| Назначение | Фиксированное имя |
|---|---|
| Снимок системных ресурсов | `hardware-snapshot.json` |
| Снимок подписочных окон | `quotas-snapshot.json` |
| Основные схемы | `telemetry/schema/hardware-snapshot.schema.json`, `quotas-snapshot.schema.json`, `bridge-output.schema.json` |
| Общие определения схем | `telemetry/schema/common.schema.json` |
| Проверочный эталон | `telemetry/tests/contract.py` |
| Синтетические примеры | `telemetry/fixtures/<scenario>/` |

Производственные файлы этапов 2–4 предназначены для приватного каталога `%LOCALAPPDATA%/DesktopWidgets/telemetry/`, по одному writer на файл. Ответ Bridge не требует третьего постоянно записываемого файла. `bridge-output.json` в репозитории — сохранённый синтетический ответ.

Диалект — [JSON Schema draft 2020-12](https://json-schema.org/draft/2020-12). Все объекты закрыты через `additionalProperties: false`; произвольные дополнительные свойства отклоняются. Схемы имеют стабильные идентификаторы в зарезервированном домене `schemas.desktop-widgets.invalid`: это идентификаторы для локального registry, а не адреса скачивания. Все четыре схемы загружаются из checkout; сетевое разрешение ссылок запрещено.

Поддерживается ровно `schemaVersion: "1.0.0"`. Неизвестная версия, включая `1.1.0`, отклоняется без догадок и частичного разбора. Это намеренно строгая начальная совместимость. Новые поля/значения перечислений и изменение смысла полей требуют новой версии схемы и явно зарегистрированного reader; breaking change увеличивает major. Исправление текста документа без изменения множества принимаемых документов не меняет wire version. Перед первым выпуском версию можно пересмотреть вместе с клиентами; автоматического преобразования здесь нет.

`policy_version: "0.1.0"` есть на верхнем уровне ответа и в `orchestration_hints`; значения должны совпадать. Это отдельная версия вычислений: изменение порога, включённой границы, причины, age/reset-логики требует новой версии политики, даже если структура JSON сохранилась. Проверочный эталон принимает только текущую версию.

## Время, единицы и неизвестное

Все timestamps — UTC, с завершающей `Z`, секундами и необязательными 1–6 десятичными знаками секунды. Смещения `+00:00`, локальное время, пробел вместо `T`, невозможные даты и leap-second в этой первой версии отклоняются. Времена измерения/попытки/публикации из будущего относительно часов reader недействительны; разрешённый future skew равен нулю. Время будущего reset допустимо. При скачке системных часов источник получает `clock_invalid`; Bridge не подправляет его времена автоматически.

| Поле | Смысл |
|---|---|
| `measured_at` метрики/окна | Время исходного наблюдения, а не чтения кэша |
| `measured_at` провайдера/снимка | Максимум исходных времён его метрик/окон; `null`, если наблюдений нет |
| `last_attempt_at` | Последняя завершённая попытка сбора; успешная и неудачная попытки могут иметь одинаковый тип timestamp |
| `published_at` | Время подготовки неизменяемого снимка, включая heartbeat |
| `generated_at` | Часы Bridge, использованные для всех вычислений конкретного ответа |
| `age_ms` | Целая часть неотрицательной разницы `generated_at − measured_at` в миллисекундах; `null`, если исходного измерения нет |

У каждого источника, провайдера и окна собственные времена. Максимум на уровне снимка не обновляет возраст старого соседнего окна. Наблюдение не может быть позднее соответствующей попытки/публикации. Для известного наблюдения нужна известная попытка. Успешное чтение старого кэша, ошибка новой попытки, повторная публикация и heartbeat сохраняют исходные `measured_at`.

Размеры памяти — целое число `bytes`, скорости — неотрицательное число `bytes_per_second`, загрузка — число `percent` в диапазоне 0–100. Температуры — `celsius` от −100 до +200 включительно; отрицательное измерение не подменяется отсутствием датчика. RTT — `milliseconds` от 0 до 60000. Верхняя граница числовых величин — не более `2^53−1`; для температур, процентов, RTT и интервалов действуют более узкие пределы схемы. Ограничение включает `duration_seconds` окна квот, счётчики пакетов и сетевых событий: integer сверх точности JavaScript отклоняется до использования. Строки с единицами, проценты строкой, `NaN`, `Infinity`, отрицательные размеры и дубликаты ключей JSON запрещены. Это UTF-8 JSON, а не JSON с комментариями.

Метрика имеет `status: ok/unknown/error/not_supported`, `reason`, `value`, `unit`, `measured_at`. Только `ok` допускает ненулевой тип значения и требует timestamp и `reason: none`. При остальных статусах `value` равен `null`, причина обязательна. Известный ноль — полноценное измерение. Неизвестное не равно нулю и не превращается в свободный ресурс. Ранее известное значение может оставаться `ok` с исходным временем после ошибки источника: состояние попытки отражается на источнике, а возраст вычисляется отдельно.

Статусы снимка/провайдера — `ok`, `partial`, `unavailable`, `error`. `partial` сохраняет доступные факты; `unavailable` не содержит пригодных значений; `error` может содержать ранее подтверждённые факты с прежними временами. Причины — закрытое перечисление, без сырого текста исключения. Структурная проверка и семантическая проверка статусов не заменяют друг друга.

## Системные ресурсы

Все перечисленные ключи обязательны, неподдерживаемые датчики передаются явно как `null` с причиной:

| Идентификатор | Единица и происхождение |
|---|---|
| `cpu_usage_percent` | `percent`, уже собранная загрузка CPU |
| `cpu_temperature_celsius`, `gpu_temperature_celsius` | `celsius`, уже имеющееся наблюдение датчика; отсутствие/неизвестное исходное время — unknown |
| `gpu_usage_percent` | `percent`, уже собранная загрузка GPU |
| `ram_total_bytes`, `ram_available_bytes` | `bytes`, физическая память и доступная физическая память |
| `commit_total_bytes`, `commit_limit_bytes`, `commit_headroom_bytes` | `bytes`, commit Windows и запас `limit − total` |
| `vram_total_bytes`, `vram_available_bytes` | `bytes`, только dedicated VRAM; shared GPU pool не подставляется |
| `gpu_memory_total_bytes`, `gpu_memory_available_bytes` | `bytes`, имеющийся GPU pool, тип задаётся `gpu_memory_kind: dedicated/shared/unknown` |
| `swap_used_bytes` | `bytes`, занятое пространство swap/pagefile из имеющегося датчика; не синоним commit |
| `network_receive_bytes_per_second`, `network_send_bytes_per_second` | `bytes_per_second`, наблюдаемый трафик |
| `network_reachability` | `reachability`, только конкретная наблюдаемая проверка |
| `gateway_rtt_ms`, `internet_rtt_ms` | `milliseconds`, раздельные пробы до шлюза и настроенного интернет-узла со своими `measured_at`, `probe_interval_ms` и фиксированными `scope: gateway/internet_probe` |

Commit headroom — разность ОС `CommitLimit` и `CommitTotal`, полученных из одного наблюдения, без пересчёта из суммы RAM и размера pagefile. Валидатор проверяет арифметику и совпадение времён трёх commit-метрик. Известный вычисленный headroom требует обоих известных исходных операндов; при неизвестном total или limit он тоже unknown, а не независимо подтверждённый запас. Дополнительно bounds `headroom ≤ limit` проверяются независимо от полноты тройки. `ram_available ≤ ram_total`, `vram_available ≤ vram_total`, `gpu_memory_available ≤ gpu_memory_total`, `commit_total ≤ commit_limit`. Размер pagefile/commit limit может изменяться. Значение headroom само по себе не гарантирует выделение памяти или успешный запуск. Основание: [Microsoft о pagefile и commit](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/introduction-to-the-page-file).

`gpu_memory_kind` описывает именно опубликованный pool существующего датчика. При `shared` общая память сохраняется в `gpu_memory_*`, а `vram_*` обязательно unknown; VRAM-pressure также unknown. При `unknown` обе группы памяти unknown. При `dedicated` известные generic/dedicated aliases должны совпадать по значению и времени. Это не двойной доступный резерв. Текущий `GpuInfo.MemShared` в `windows/resources-widget/src/Model.cs` позволяет сделать различие без нового датчика. Температурные поля и GPU load сохраняют видимые факты; температурного автопилота или thermal routing политика не вводит.

У reachability `value` — `reachable`, `unreachable` или `null`; обязательный `scope` — `not_measured`, `gateway`, `internet_probe` или `provider_probe`. Только `provider_probe` требует `provider_id`, в остальных случаях он `null`. `ok` требует измеренного scope и времени. Нет измерения — `scope: not_measured`, `value: null`, `status: unknown`. Пакеты/линк/ответ одного адреса не доказывают доступность всех провайдеров. Общего `network_ready` контракт не имеет. Bridge не добавляет сетевую пробу при запросе.

RTT имеет собственный cadence: свежесть строго `age_ms < max(5000, 3 × probe_interval_ms)`, где `probe_interval_ms` берётся из действующей настройки пинга, не из `sample_interval_ms`. Это сохраняет строгую границу существующего `NetJournal.Health`. Для `ok` известны исходное время успешного ответа и probe interval; неизвестный интервал или недоступное исходное время не заменяются временем последнего Sample. В этапе 2 потребуется передать существующие `lastPingAt`/`lastGwAt` вместе с уже имеющимися `PingMs`/`GatewayMs`: текущий Sample не раскрывает эти private timestamps. До этого RTT unknown. Ни нового pinger, ни HTTP probe, ни проверки провайдера контракт не запускает.

Отдельный `network_quality` сохраняет уже имеющиеся дневные `PingSent/PingLost`, `GwSent/GwLost`, `Outages`, `Disconnects` из `NetJournal`. Это закрытый объект с `status`, `reason`, `measured_at`, `window_kind: local_calendar_day`, UTC-границами `window_start`/`window_end` и `coverage_scope: widget_observed_only`. Границы — местные полуночи существующего журнала, переведённые в UTC с действовавшими смещениями, интервал `[start,end)`. Это календарный день, включая 23/25 часов при переходе времени, а не выдуманное rolling window. Проверка допускает положительный интервал до 26 часов; соответствие полуночам обеспечивает adapter источника. Future window end допустим; исходное наблюдение должно находиться внутри окна и не быть из будущего.

Поля `internet_sent`, `internet_lost`, `gateway_sent`, `gateway_lost`, `outages_count`, `disconnect_count` — целые counts либо `null`, единица `count_unit: count`. Loss передаётся в `internet_loss_percent`/`gateway_loss_percent`, `loss_unit: percent`; формула `100 × lost/sent`, `lost ≤ sent`, допуск 0.001 процентного пункта. При `sent = 0` либо неизвестных sent/lost loss обязательно `null`, а не 0%. Такая частичная известность имеет `status: partial` с причиной. Полностью известный `ok` требует ненулевого числа проб обоих scope и всех числовых фактов.

`coverage_seconds`, `coverage_unit: seconds` — сколько секунд виджет наблюдал этот календарный день; покрытие не может превышать прошедшую часть окна. Счётчики не доказывают непрерывный мониторинг всего дня. В `hardware_state.network_quality` вычисляются отдельные `age_ms`/freshness по собственному `measured_at` и hardware-порогу; свежий Sample/heartbeat не обновляет исходное время counters. Если текущая передача `DayPeaks` не содержит достоверного времени наблюдения, этап 2 должен явно передать его из источника либо оставить quality unknown. Raw event text, адрес шлюза и probe hostname в JSON не переносятся.

`sample_interval_ms` повторяет действующий `intervalMs` производителя. Производитель использует уже собранные значения и single-slot latest-value: новый готовый снимок заменяет ожидающий; очередь старых снимков не накапливается. Публикация не чаще 1 Гц и только после готовых измерений. Большой `intervalMs` не ускоряется ради Bridge. Объект, переданный writer, больше не мутируется. Ошибка записи не ломает сбор и интерфейс. Метрики, обновляемые реже при скрытом UI, сохраняют собственное время или становятся unknown.

## Подписки и окна

Иерархия — `providers[] → pools[] → windows[]`; `model_ids[]` принадлежат пулу. Ключ окна — тройка `provider_id + pool_id + window_id`. Повтор провайдера, пула внутри провайдера или окна внутри пула запрещён семантически. Provider IDs этой версии: `codex`, `claude`, `antigravity`, `gemini`, `kimi`. Остальные IDs — контролируемые slug до 64 символов, начинающиеся с латинской строчной буквы; допустимы цифры, точка, дефис, подчёркивание. Это внутренние идентификаторы адаптера, не display label и не имя аккаунта. Менять их вслед за переводом/оформлением полосы запрещено. Добавление провайдера требует новой схемы; новые стабильные pool/model/window IDs не меняют смысл существующих.

Несколько моделей могут расходовать один pool. Контракт не делит окно на агентов и не суммирует квоты моделей. `duration_seconds` — положительное целое либо `null`, если длительность неизвестна; это не остаток времени до reset. У окна собственные `status`, `reason`, `measured_at`, `last_attempt_at`, `used_percent`, `remaining_percent`, `resets_at`. Для `ok` обе доли известны, лежат в 0–100 и дают 100 с допуском 0.001 процентного пункта на округление. При unknown/error/not_supported доли равны `null`.

Опрос провайдеров сохраняется: по умолчанию `poll_interval_ms = 300000`, допустимый минимум 60000. Источники завершаются независимо; публикация одного провайдера не ждёт всех остальных. Heartbeat версии 1.0.0 фиксирован: `heartbeat_interval_ms = 10000`. Он обновляет только `published_at` и состояние публикатора, не выполняет provider calls и не обновляет время квот. Это принятое начальное значение в предложенном диапазоне 5–10 секунд; изменение значения требует явного обновления схемы/политики.

Bridge рассчитывает `reset_time_passed_unverified` отдельно для каждого окна:

- `true`: reset уже наступил, но последнее наблюдение относится к времени строго до него;
- `false`: известные времена не требуют ожидания подтверждения; включая наблюдение в момент reset или после него;
- `null`: время reset или исходного наблюдения неизвестно, заключение сделать нельзя.

Свежая публикация/heartbeat, визуальный сброс полосы и чтение старого кэша не снимают флаг. Обнуление/восстановление доли требует реального наблюдения окна. В выходном плоском массиве `remaining_percent` — пригодный для решения факт: он передаётся только при свежем наблюдении и флаге `false`; stale/pending/unknown дают `null`. Исходная наблюдаемая доля сохраняется в `source`, со своим временем и статусом. Это не вывод о том, сколько новых исполнителей можно запустить.

## Ответ и независимые состояния

Помимо `schemaVersion`, `mode`, `generated_at`, `policy_version` ответ содержит ровно четыре смысловых узла: `hardware_state`, `subscription_quotas`, `api_limits`, `orchestration_hints`. Валидация не допускает scheduler, leases, зарезервированных слотов, рекомендованного количества workers, команд или routing.

Первые два узла содержат `source` — целиком валидированный allowlisted снимок либо `null`; `read_status`, `status`, `reason`, `liveness`, `freshness`. В `hardware_state.metrics` лежат возраст/свежесть каждой метрики, в `hardware_state.network_quality` — возраст/свежесть дневного наблюдения; в `subscription_quotas.windows` — возраст/свежесть, идентичность и reset-состояние каждого окна.

| Ось | Значения и трактовка |
|---|---|
| `read_status` | `ok`, `missing`, `invalid_input`, `clock_invalid`, `transient_io_error`, `access_denied` |
| `liveness` | `alive`: публикация укладывается в порог; `silent`: порог превышен; `unknown`: нет подтверждённой публикации |
| `freshness` | `fresh`, `stale`, `unknown`, по исходному измерению, независимо от публикации |

На уровне узла любое старое известное измерение даёт `stale`; иначе наличие свежего измерения даёт `fresh`; иначе `unknown`. Частично неизвестные метрики не теряются из-за агрегата: их состояния остаются на своих ключах. Снимок с `status: ok` понижается до `partial`, если публикатор молчит, данные stale или некоторые измерения unknown. Ранее сохранённый `error`/`partial` не повышается автоматически из-за свежего heartbeat.

При ошибке чтения и наличии ранее проверенного кэша `source` сохраняет исходные timestamps, возраст продолжает расти, `status: error`, причина отражает чтение. При холодном отсутствии файла — `source: null`, `status: unavailable`, `read_status: missing`. При холодной ошибке разбора/доступа — `source: null`, `status: error` с конкретным allowlisted кодом. Отсутствие heartbeat не доказывает, что человек закрыл окно. Недействительный новый снимок никогда не становится кэшем и не заменяет проверенную версию.

`api_limits` имеет только `status: not_available`, `reason: monitor_not_implemented`. Подписочные квоты не содержат API-стоимость, кредиты, тарифные бюджеты и валюту. Отсутствующий API-монитор не означает нулевые расходы или свободный бюджет.

## Начальная политика 0.1.0

Числа ниже точны и проверяемы, но это исходная диагностическая политика этапа 1. Она выявляет давление/качество фактов; это не оценка безопасного числа процессов и не гарантия достаточной памяти для конкретной сборки. Критерий безопасного запуска конкретной работы требует её профиля и остаётся у существующего Root.

| Параметр | Граница версии 0.1.0 | Основание и предел вывода |
|---|---|---|
| Свежесть hardware | `age_ms ≤ max(5000, 3 × sample_interval_ms)` | Три периода допускают задержку публикации; минимум 5 секунд покрывает предел 1 Гц. Большой `intervalMs` увеличивает диагностическое окно, а не обещает актуальность каждую секунду |
| Hardware liveness | `publication_age_ms ≤ max(5000, 3 × sample_interval_ms)` | У hardware нет отдельного heartbeat; публикация зависит от готовых измерений |
| Свежесть RTT | `age_ms < max(5000, 3 × probe_interval_ms)` | Самостоятельный probe cadence и исходное время; граница совпадает с действующим NetJournal.Health |
| Свежесть quota window | `age_ms ≤ max(900000, 3 × poll_interval_ms)` | Три штатных 300-секундных цикла; минимальная настройка 60 секунд не превращает старую квоту в свежую через heartbeat |
| Quota liveness | `publication_age_ms ≤ 30000` | Три 10-секундных heartbeat |
| Physical-memory pressure | high при `available/total ≤ 10%`; elevated при `≤ 20%`; иначе normal | Сигнал малой доли физического резерва; абсолютный объём и рабочий профиль по-прежнему существенны |
| Commit pressure | high при `headroom/limit ≤ 5%`; elevated при `≤ 10%`; иначе normal | Независимый сигнал близости commit limit, не оценка свободной RAM |
| VRAM pressure | high при `available/total ≤ 5%`; elevated при `≤ 10%`; иначе normal | Только если обе метрики известны и свежи |
| CPU pressure | high при `usage ≥ 95%`; elevated при `≥ 85%`; иначе normal | Моментная загрузка, без прогноза длительности |

Нулевой знаменатель, неизвестная или старая нужная метрика дают `level: unknown` с причиной; это не normal. Каждый pressure содержит `inputs` с ID, фактическим значением, единицей и исходным временем, а также детерминированный reason. Нормальный pressure не является разрешением запуска. Кратковременные пики без истории не подтверждают устойчивую перегрузку.

`data_quality` — набор закрытых кодов `hardware_unavailable`, `hardware_stale`, `quotas_unavailable`, `quotas_stale`, `publisher_silent`, `unknown_metrics`, `quota_reset_unverified`. Подробная причина ошибки сбора/чтения остаётся в соответствующем узле/источнике. Корпус раздельно подтверждает low RAM при большом commit и малый commit headroom при достаточной RAM.

Калибровка этапа 1 ограничена детерминированными граничными тестами, фактическим cadence из проекта и измерениями fixture-прототипа в companion-документе. Размер нормального примера после проверки полноты: hardware 4702 bytes, quotas 1602 bytes, output 12409 bytes (форматированные UTF-8 файлы этого корпуса). Измерения latency/CPU/RAM файлового прототипа не доказывают адекватность pressure-порогов для каждой реальной сборки. Live-калибровка производителей и пилот относятся к последующим этапам; изменение границ версионируется.

Root использует достоверные остальные данные при частичном отказе. Обычная ограниченная работа допустима с отмеченной неопределённостью; тяжёлое расширение параллелизма при неизвестном критическом резерве откладывается. Нет бесконечного ожидания, provider refresh, ротации аккаунтов или автоматического расходования API.

## Контракт файлового обмена для следующих этапов

1. Writer создаёт временный файл в той же приватной локальной папке с эксклюзивным handle, полностью записывает снимок, закрывает handle и затем заменяет target. Существующий target никогда не удаляется перед заменой. Первое создание при отсутствующем target — отдельная операция с отдельной проверкой результата. Писатель один на источник.
2. C# reader рекомендуется открывать неизменяемый файл с `FileAccess.Read` и `FileShare.Read | FileShare.Delete`, быстро читать и закрывать. `FileShare.Write` ему не требуется: существующий target не редактируется на месте. Node/libuv может использовать собственные default sharing flags `Read | Write | Delete`; это совместимость handle, а не выдача права на запись и не изменение ACL. Семантика всех reader остаётся read-only, writer не редактирует target на месте, handles закрываются быстро. От Node не требуется API для буквального воспроизведения C# flags. Права папки — отдельная проверка; sharing flags их не заменяют. Основание: [Microsoft FileShare](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileshare?view=netframework-4.8.1).
3. Начальная retry policy: максимум 4 попытки включая первую, задержки перед повторами 1, 2 и 4 ms, общий monotonic retry deadline 25 ms. Проверка deadline выполняется перед каждой новой попыткой; новое ожидание/попытка после deadline не стартует. Только установленные sharing/lock collision коды Windows 32/33 допускают retry. Ошибка доступа, версия/схема, clock-invalid и отсутствующий cold target не повторяются. Синхронный системный вызов сам может превысить deadline: 25 ms ограничивают retry scheduling, а не дают жёсткую верхнюю границу задержки ОС. Прототип этапа 1 не доказывает надёжность Win32 replace/recovery; это проверка этапа 4.
4. После read-failure разрешён только ранее проверенный кэш с исходным возрастом и соответствующим `read_status`; холодный reader возвращает unknown/unavailable/error. Не пытаться восстановиться чтением временного файла или частичного JSON. Разные исходы сбоя ReplaceFile требуют явной проверки target/temp/backup перед очисткой; сохранность target при любом отказе не обещается. Основание: [Microsoft ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).
5. Каталог определяется один раз при запуске: `--telemetry-dir` → `DESKTOP_WIDGETS_TELEMETRY_DIR` → стандартный каталог. Только абсолютный локальный путь; arbitrary path в запросе MCP отсутствует. Ни один вызов читателя не опрашивает ОС или провайдеров. Бюджет входа начального reader — не более 1 MiB на снимок до JSON parsing; превышение — `invalid_input`, без тихого усечения. Это защитный предел, а не целевой размер нормальной публикации.

У производителей сохраняются C# 5, существующий .NET Framework и `JavaScriptSerializer`, без зависимостей от Python/Node/валидатора. Эти требования предстоит проверить сборкой в этапах 2–3. Публикационный heartbeat не оправдывает постоянное перестроение больших provider payloads; immutable latest value и публикация уже полученных результатов обязательны.

## Безопасность и режим фикстур

Разрешены только поля схем. Нельзя включать credentials, tokens, cookies, аккаунты/почту, raw provider strings, command lines, имена пользователей, private host paths и UI state. Для IDs используются константы/реестр адаптера, а не значения из произвольных строк провайдера. Схема ограничивает форму полей и не может распознать секрет, намеренно закодированный под допустимый slug: allowlisted extraction остаётся обязательством производителя. Raw provider response и рабочий `state.json` в корпус не копируются.

Ошибки validator CLI не печатают отвергнутый JSON, значения полей или исключения целиком. Приватность проверяется негативными тестами extra fields на каждом уровне. Обработка ACL, symlinks/reparse points, ownership и окончательные bounds ввода требуют отдельной runtime-проверки этапа 4; текущие схемы сами по себе этого не реализуют.

Каждый снимок и ответ несёт явный `mode: fixture/live`. Нестандартный путь сам по себе не включает fixture mode. В корпусе все данные придуманы, все timestamps фиксированы, никакой live источник не читался. `manifest.json` содержит `synthetic: true`, `as_of: 2026-01-01T12:00:00Z`; при воспроизведении используется именно этот clock. Смешивание fixture/live отвергается. Ошибка fixture никогда не вызывает fallback к реальному источнику. Старые live-факты не получают новый `generated_at` как замену своему `measured_at`.

## Проверки и воспроизведение

Проверено локальным полным валидатором `jsonschema 4.26.0` с draft-2020-12, `FormatChecker` и offline `referencing 0.37.0`, уже установленными в среде. Версии для воспроизведения закреплены в `telemetry/tests/requirements.txt`; это зависимости проверки контракта, не новая зависимость производителей. [Документация python-jsonschema](https://python-jsonschema.readthedocs.io/en/stable/validate/) отдельно предупреждает, что `format` без checker является аннотацией, поэтому checker включён явно.

Для PowerShell в корне checkout; исполнитель — Codex. Команда не устанавливает зависимости и не обращается к провайдерам:

```powershell
python -m unittest discover -s telemetry/tests -v
```

Для PowerShell в корне checkout; исполнитель — Codex. Детерминированная проверка отдельного ответа:

```powershell
python telemetry/tests/contract.py bridge-output telemetry/fixtures/normal/bridge-output.json --as-of 2026-01-01T12:00:00Z
```

Для PowerShell в корне checkout; исполнитель — Codex. Перегенерация только синтетического корпуса, без live fallback:

```powershell
python telemetry/tests/generate_fixtures.py
```

Схемы проверяют типы, перечисления, диапазоны, единицы, обязательность, неизвестные поля и формат UTC. Отдельный semantic layer проверяет future clock, порядок/агрегацию времён, арифметику commit/процентов, неполные commit-операнды, dedicated/shared GPU memory, RTT cadence, дневные границы/покрытие/loss, идентичность окон, fixture/live isolation и полное равенство derived output детерминированной политике. JSON Schema не заявляется способной самостоятельно сравнивать часы, соседние поля или пересчитывать hints.

Корпус содержит 10 сценариев: normal, partial, offline, quota-reset-pending, low-physical-memory, high-commit-pressure, stale-with-heartbeat, unknown-metrics, publisher-silent, cold-read-unavailable. Отрицательные случаи создаются в памяти тестов: лишние поля с synthetic markers, неверная версия/единица/процент/размер/время, дубликаты IDs/JSON keys, подделка hints, несогласованные measured/attempt times, неизвестный reset, ошибка чтения с кэшем и без кэша. Это подтверждение контракта, а не доказательство атомарного Windows writer, установки MCP в действующую сессию или приёмки в реальной работе.
